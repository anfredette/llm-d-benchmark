# LLM-D Benchmark CSV Field Reference

This document describes the fields in the CSV files generated by the LLM-D benchmark harness.

## 📊 CSV Column Descriptions

| Column | Description | Unit | vLLM Metric Equivalent |
|--------|-------------|------|------------------------|
| **`prompt_tokens`** | Number of input tokens in the request prompt | tokens | Input token count |
| **`generation_tokens`** | Number of output tokens generated by the model | tokens | Output token count |
| **`ttft`** | **Time to First Token** - Latency from request start until first token appears | seconds | `mean_ttft_ms` (but in seconds) |
| **`generation_time`** | Time spent generating all output tokens (excludes TTFT) | seconds | Generation phase latency |
| **`user_id`** | Identifier for the simulated user making the request | integer | Concurrency tracking |
| **`question_id`** | Identifier for the specific question/prompt used | integer | Test case tracking |
| **`launch_time`** | Unix timestamp when the request was initiated | seconds.microseconds | Request start time |
| **`finish_time`** | Unix timestamp when the request completed | seconds.microseconds | Request end time |
| **`Delta`** | Total end-to-end request time (`finish_time - launch_time`) | seconds | Total request latency |

## 🔍 Core Performance Metrics

### Primary Latency Metrics
- **`ttft`** - Critical for interactive applications; time until user sees first response
- **`generation_time`** - Time to complete the response after first token
- **`Delta`** - Total request latency including all processing overhead

### Token Counts
- **`prompt_tokens`** - Input size; affects TTFT significantly  
- **`generation_tokens`** - Output size; affects generation_time linearly

### Tracking Fields
- **`user_id`** - Tracks concurrent requests (higher numbers = more concurrency)
- **`question_id`** - Identifies different prompt templates or test scenarios

## ⏱️ Timestamp Format

The `launch_time` and `finish_time` fields use **Unix timestamps with microsecond precision**:

**Format**: `seconds.microseconds` since January 1, 1970, 00:00:00 UTC

**Example**:
```
launch_time: 1754341548.773472
finish_time: 1754341552.2659733
```

- **Integer part** (`1754341548`): Seconds since Unix epoch
- **Decimal part** (`.773472`): Microseconds (6 decimal places)
- **Precision**: Accurate to 0.000001 seconds (1 microsecond)

## 🧮 Derived Metrics You Can Calculate

### Time Per Output Token (TPOT)
```
TPOT = generation_time / generation_tokens
```
*Average time to generate each output token*

### Inter-Token Latency (ITL)
```
ITL = generation_time / generation_tokens
```
*Time between consecutive tokens (same as TPOT for this benchmark)*

### Normalized Time Per Output Token (NTPOT)
```
NTPOT = (ttft / generation_tokens) + TPOT
```
*Amortized per-token cost including prompt processing*

### Output Token Throughput
```
Output_TPS = generation_tokens / generation_time
```
*Tokens generated per second (generation phase only)*

### Total Token Throughput
```
Total_TPS = (prompt_tokens + generation_tokens) / Delta
```
*All tokens processed per second (including input)*

### Request Validation
```
Expected_Delta = ttft + generation_time
Actual_Delta = finish_time - launch_time
```
*These should be approximately equal*

## 📈 Performance Analysis Examples

### Sample Data Row
```csv
prompt_tokens,generation_tokens,ttft,generation_time,user_id,question_id,launch_time,finish_time,Delta
21047.0,100.0,1.8632,1.6292,3,1,1754341548.773472,1754341552.2659733,3.4927
```

### Analysis
- **Input**: 21,047 tokens (long-input scenario)
- **Output**: 100 tokens generated  
- **TTFT**: 1.86 seconds (processing 21K input tokens)
- **Generation**: 1.63 seconds (producing 100 output tokens)
- **TPOT**: 1.63/100 = 0.0163 seconds per token (16.3ms/token)
- **Total time**: 3.49 seconds end-to-end
- **Latency breakdown**: 53% TTFT, 47% generation

### Performance Insights
- **Long prompts** → High TTFT (input processing dominates)
- **Short prompts** → Low TTFT (generation dominates)  
- **Higher QPS** → Increased latency across all metrics
- **Consistent TPOT** → Model is generating tokens at steady rate

## 🎯 Mapping to Standard vLLM Metrics

| LLM-D Benchmark | vLLM Standard | Conversion |
|----------------|---------------|------------|
| `ttft` | `mean_ttft_ms` | `ttft * 1000` |
| `generation_time / generation_tokens` | `mean_tpot_ms` | `(generation_time / generation_tokens) * 1000` |
| `generation_time / generation_tokens` | `mean_itl_ms` | `(generation_time / generation_tokens) * 1000` |
| `Delta` | End-to-end latency | Direct use |
| Aggregated across file | `request_throughput` | `count(requests) / total_time` |
| Aggregated across file | `output_token_throughput` | `sum(generation_tokens) / total_time` |

## 📊 Multi-QPS Analysis

When comparing across different QPS files (`0.1.csv`, `0.25.csv`, `0.5.csv`):

### Expected Patterns
- **Low QPS (0.1)**: Minimal queuing, best latency
- **Medium QPS (0.25)**: Some queuing, moderate latency increase  
- **High QPS (0.5)**: Significant queuing, potential saturation

### Key Comparisons
1. **TTFT degradation** - Shows input processing bottlenecks
2. **Generation time consistency** - Token generation should remain stable
3. **Delta vs sum(ttft + generation_time)** - Reveals queuing overhead
4. **User ID spread** - Higher max user_id indicates more concurrency

## 💡 Analysis Tips

### Data Quality Checks
```bash
# Verify data consistency
awk -F',' 'NR>1 {delta=$9; calculated=$3+$4; diff=delta-calculated; print diff}' file.csv

# Find outliers in TTFT
awk -F',' 'NR>1 {print $3}' file.csv | sort -n | tail -5

# Calculate average TPOT
awk -F',' 'NR>1 {sum+=$4/$2; count++} END {print sum/count}' file.csv
```

### Performance Investigation
- **High TTFT variation** → Input processing bottlenecks
- **High generation_time variation** → Model instability or resource contention  
- **Delta >> (ttft + generation_time)** → Queuing delays
- **Constant TPOT across load levels** → Good generation stability
